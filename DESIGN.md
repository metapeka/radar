# DESIGN.md — правила оформления вики

Документ для разработки: как устроен сайт, какие компоненты есть, что можно и чего нельзя. Обновлять при каждом изменении вёрстки.

**Стек:** статический HTML, генерируется из Markdown скриптом `tools/build_site.py` через pandoc. Никаких фреймворков, сборка на стороне GitHub. Публикация — `docs/` из ветки `master`, GitHub Pages.

```
site/content/*.md   →  pandoc  →  site/template.html  →  docs/*.html
site/assets/*.css   →                                   docs/assets/
site/data/*.json    →  SVG-графики                      docs/assets/charts/
provenance/*.json   →  страница статуса                 docs/sources.html
site/content/*.md   →  Atom                             docs/feed-*.xml
```

## 1. Принципы

1. **Читается без JS.** Всё содержимое и навигация работают при отключённом JavaScript; скрипты только улучшают.
2. **Работает офлайн.** Никаких CDN, внешних шрифтов и API. Всё лежит в репозитории.
3. **Печатается.** Отчёт должен нормально выглядеть на A4 без отдельной вёрстки.
4. **Не мешает.** Анимации минимальны и отключаются системной настройкой.
5. **Один источник правды.** Данные для графиков — в `site/data/*.json`, а не в тексте страниц.

| `--bg-soft` | `#efece3` | `#10161a` | Панели, таблицы |
| `--fg` | `#13171b` | `#e6ece8` | Основной текст |
| `--muted` | `#5a636c` | `#93a19b` | Второстепенный текст |
| `--line` | `#d7d1c3` | `#1f2b2c` | Границы |
| `--accent` | `#0b6b5b` | `#5eead4` | Ссылки, акценты |
| `--accent-soft` | `#e1efea` | `#0c2a26` | Подсветка |

Контраст проверен по WCAG: основной текст ≥ 7:1, второстепенный ≥ 5:1, акцент ≥ 4.5:1 на всех фонах, включая `--bg-soft`.

## 3. Типографика

- Базовый размер 16.5 px, интерлиньяж 1.62, ширина текста ≤ 840 px.
- Шкала: h1 34 px (26 px на мобильном), h2 21 px, h3 16.5 px. Пропускать уровни нельзя.
- Код и пути — моноширинный, 13.2 px в блоке. Моноширинным набраны подписи: разделы навигации, даты, статусы, номера приоритетов и заголовки таблиц. Это оформление, а не смысл: без CSS текст читается так же.
- У h2 на странице есть номер `01`, `02`… — CSS-счётчик, в тексте его нет. Нумерация помогает удерживать место в длинной странице.
- Максимум одна мысль в абзаце; списки — для перечислений, не для прозы.

## 4. Компоненты

### Callout

Четыре типа. В Markdown — fenced div:

```markdown
::: {.callout .warning}
Ключ невозможно восстановить. Сохраните его вне телефона.
:::
```

| Класс | Когда | Вид |
|---|---|---|
| `.note` | Пояснение, контекст | синяя полоса |
| `.warning` | Риск потери данных или доступа | оранжевая |
| `.ok` | Что работает, подтверждено | зелёная |
| `.myth` | Разбор заблуждения | серая, курсив |

Правило: не больше двух callout на экран, иначе перестают читаться.

### Бейджи приоритетов

В таблицах `P0`, `P1`, `P2` автоматически превращаются в цветные чипы при сборке. В тексте писать словами: «приоритет P0».

### Дата проверки

Под `h1` на каждой странице — строка `проверено 23.11.2026` (класс `.verified`, `<time datetime>`). Дата означает день последней сверки фактов с источниками, а не дату публикации источника и не дату правки.

Хранится не в Markdown, а в `site/data/verified.json`: ключ — slug страницы, значение — `ГГГГ-ММ-ДД`. Правка текста не двигает дату; двигает только сверка. Страница без ключа собирается без бейджа, сборка печатает предупреждение; битая дата останавливает сборку. Расхождение с историей git проверяет `python3 tools/check_verified.py`.

### Страницы из данных

`docs/sources.html` («Здоровье источников») не имеет Markdown-исходника: сборка строит её из `provenance/sources.json`. Править текст в HTML бессмысленно — перезапишется. Такие страницы перечислены в `GENERATED` в `tools/build_site.py`; дата проверки им не нужна.

`docs/services.html` («Каталог сервисов») и блоки чек-листов собираются из `site/data/services.json`. В исходнике страницы сервиса стоит строка `[Чек-лист на сайте](URL) <!--services:slug-->`: на сайте она заменяется блоком, в Markdown на GitHub остаётся осмысленной ссылкой на собранную страницу. Сам чек-лист в Markdown не дублируется. Сборка падает, если у пункта нет приоритета или группы, если slug повторяется или у сервиса нет пунктов.

### Главная: статистика, шаги, карта

Главная — одна непрерывная страница: статистика, три шага, карточки, карта разделов. Числа в статистике подставляет сборка из `services.json` и `verified.json` (маркеры `<!--stat:services-->` и т.п.), вручную их не пишут.

- `.hero-stats` — три числа с моноширинными подписями.
- `.steps` / `.step` — три шага с временем; на мобильном одна колонка.
- `.map` — карта разделов в две колонки, на мобильном одна.

### Карточки

Только на главной, для навигации. Разметка — обычный HTML-блок в `index.md`:

```html
<div class="cards">
  <a class="card" href="ios.html"><b>iOS</b><span>Версии, SDP, Lockdown, MVT</span></a>
</div>
```

### Крошки

Генерируются сборкой: `Главная / Платформы`. Руками не писать.

### Чек-листы

Стандартный markdown task list. Скрипт добавляет сохранение отметок в браузере и счётчик «сделано N из M» с кнопкой сброса. Ничего дополнительно размечать не нужно.

### Профили риска

Три режима: обычный, повышенный, целевой. Переключатель — в сайдбаре, выбор хранится в `localStorage`.
Блок помечается fenced div: `::: {.profile .elevated}` или `.targeted`. В HTML блок остаётся всегда и скрывается CSS,
поэтому печать, поиск и читалка без JS его видят. При переходе по ссылке внутрь скрытого блока профиль
переключается автоматически.

Правила отнесения пунктов к профилям — в [RISK-MODEL.md](RISK-MODEL.md). Там же паспорт пункта и проверки.

### Таймлайн

Хронология исследований или инцидентов — список дат, свёрнутый по умолчанию. Дата в `<time datetime="2026-11-21">`, в тексте — «21 ноября 2026». В свёрнутом виде видно дату, заголовок и одну строку результата; подробности и мини-таблица находок — внутри.

```html
<p class="timeline-actions"><button type="button" data-tl-toggle aria-pressed="false">Развернуть всё</button></p>
<ol class="timeline">
<li><details class="tl">
<summary>
  <time datetime="2026-05-18">18 мая 2026</time>
  <span class="tl-title">Заголовок</span>
  <span class="tl-note">Одна строка результата</span>
</summary>
<div class="tl-body">
  <ul><li>Тезис.</li></ul>
  <p class="tl-src"><a href="…">Источник</a></p>
</div>
</details></li>
</ol>
```

Правила: один пункт — одно событие; ссылка на первоисточник, не на пересказ; внутри — `<b>` и списки, без `h3`, чтобы оглавление не распухало. Кнопка «Развернуть всё» необязательна для чтения: без JS блоки раскрываются кликом. Перед печатью скрипт раскрывает все пункты. Стили — `.timeline`, `.tl-*`, `.timeline-actions`. Таймлайн не заменяет таблицу источников.

### Таблицы

- Первая строка — заголовки, `scope="col"` добавляется сборкой.
- Больше 5 колонок — плохая идея: на мобильном уходит в скролл.
- Числа выравнивать по правому краю нельзя (нет разметки), поэтому единицы пишем в заголовке.
- Если в шапке есть три и более платформы (macOS, Windows, Linux, iOS, Android), скрипт сам добавляет фильтр: кнопки «Все / macOS / …» скрывают строки, где в этой колонке стоит «—». Размечать ничего не нужно.

### Графики

- Только SVG, сгенерированный при сборке из `site/data/*.json`.
- Обязательны: подпись под графиком, источник данных, дата среза.
- Никаких библиотек на клиенте: график — картинка, доступная для печати и скринридера (`alt`).
- Если данных на серию нет — таблица, а не график.

## 5. Контент-правила

- **Emoji:** один маркер на заголовок раздела максимум, не в таблицах и не в навигации. Для статусов — бейджи, не эмодзи.
- **Даты:** `9 ноября 2026` в тексте, `2026-11-09` в данных.
- **Ссылки:** текст ссылки осмысленный, не «здесь».
- **Цифры:** с единицей измерения и источником; оценки помечать словом «оценка».
- **Уверенность:** подтверждено / один источник / оценка / не найдено — как в [методике](https://metapeka.github.io/whatsapp-security-research/methodology.html).
- **Никаких «просто», «легко», «все знают».** Читатель пришёл за проверяемым.

## 6. Две поверхности: Pages, Markdown и Issues

Один исходник читают в трёх местах: собранный сайт, просмотр `.md` в репозитории и вставка фрагмента в Issue. Сайт — основная витрина, но страница обязана оставаться понятной, если убрать CSS и JS.

Правила фиксации источников — в [provenance/README.md](provenance/README.md): публичный манифест с хешами и приватные снапшоты.

| Что | Pages | Markdown на GitHub | Issue |
|---|---|---|---|
| CSS, классы | работают | игнорируются | игнорируются |
| `<details>` / `<summary>` | работает | работает | работает |
| Таблицы, ссылки | работают | работают | работают |
| JS, localStorage | работает | нет | нет |
| Fenced div `:::` | стилизуется | виден как текст | виден как текст |
| Относительные ссылки | работают | работают в репозитории | ломаются |

### Правила

1. **Смысл — только в тексте.** Статус, приоритет и предупреждение пишутся словами. Цвет, бейдж и иконка — украшение; без них страница не теряет смысла.
2. **Разрешённый HTML:** `details`, `summary`, `time`, `table`, `a`, `code`. Остальное GitHub вырежет или покажет как текст.
3. **Callout деградирует в `:::`.** Текст внутри должен читаться без рамки; заголовок дублируется словами («Важно:», «Проверено:»).
4. **Внутри HTML-блока Markdown не парсится.** В таймлайне списки и таблицы размечены HTML, а не `-` и `|`; иначе на GitHub они останутся сырым текстом.
5. **Таблицы — до 4 колонок.** Шире — в Issue уезжает в горизонтальный скролл.
6. **Внешние источники — полным URL.** Относительные ссылки (`max.html`) работают на сайте и в репозитории, но в Issue мертвы.
7. **Ничего, что появляется только по JS.** Раскрытие, навигация и поиск должны иметь смысл без скриптов; `details` работает нативно.

### Issues как трекер

Сайт — снимок, Issues — обсуждение и история. Автоматической синхронизации нет.

- Одна issue — одно событие или одна находка; не сваливать волну исследования в один тред.
- Заголовок: `[MAX] 18.05.2026 — большой реверс APK`.
- Шаблон issue: дата, источник (URL), что обнаружено, статус, что изменить на странице.
- Метки: `max-research`, `confirmed`, `unconfirmed`, `open`, `page-update`.
- Статусы — те же слова, что в [методике](https://metapeka.github.io/whatsapp-security-research/methodology.html): подтверждено / один источник / оценка / не подтверждено.
- Закрытие issue не меняет страницу. Правило: закрыл — обновил страницу и дату сверки в том же PR.
- Страница ссылается на issue полным URL, issue — на страницу.
- Автоматическая сборка из Issues не делается: это ломает офлайн-сборку и требует токена.

## 7. Доступность (обязательно)

- Видимый `:focus-visible` у всех интерактивных элементов, кольцо ≥ 3:1.
- Контраст текста ≥ 4.5:1, крупного ≥ 3:1.
- Модальное окно поиска: ловушка фокуса, возврат фокуса, `aria-modal`, `inert` на фоне.
- Мобильное меню: перенос фокуса, блокировка прокрутки, закрытие по Esc.
- Таблицы: `caption`, `scope="col"`, прокручиваемый контейнер с `tabindex="0"` и именем.
- `prefers-reduced-motion` отключает плавную прокрутку и переходы.
- Порядок заголовков без пропусков; landmark-роли `header`/`nav`/`main`/`footer`.

## 8. Производительность

| Метрика | Бюджет |
|---|---|
| CSS | ≤ 25 КБ |
| JS | ≤ 25 КБ |
| Одна страница HTML | ≤ 40 КБ |
| Внешние запросы | 0 |
| График SVG | ≤ 20 КБ |

Проверка: `du -b docs/assets/*.css docs/assets/*.js`, размер страниц — в конце сборки.

## 9. Как добавить страницу

1. Создать `site/content/<slug>.md`, первая строка — `# Заголовок`, затем цитата-лид.
2. Добавить `(slug, "Название")` в `NAV` в `tools/build_site.py`.
3. При необходимости — ссылку в `index.md`.
4. Собрать: `python3 tools/build_site.py`.
5. Проверить: битые ссылки, h1, мобильную вёрстку, фокус с клавиатуры и просмотр `.md` на GitHub — таблицы и `<details>` должны читаться без стилей.
6. Записать изменение в `site/content/updates.md`: дата, что изменилось, ссылки на страницы.
7. Коммит и пуш — Pages пересоберётся сам.

Сборка падает, если у страницы нет `# Заголовка`: это защита от пустых файлов.

## 10. Чего не делать

- Не подключать внешние библиотеки и шрифты.
- Не делать SPA и клиентский роутинг.
- Не использовать `display:none` для контента, который нужен скринридеру.
- Не дублировать данные: график и таблица должны читать один JSON.
- Не менять `--accent` без пересчёта контраста.
- Не прятать смысл в CSS-классы, бейджи и цвет: в Issues их нет.
- Не делать fenced div единственным носителем предупреждения — текст должен читаться и как `:::`.
- Не ссылаться на внутренние страницы относительным URL в тексте, который может уйти в Issue.
