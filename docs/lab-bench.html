Стенд для анализа

Отдельная сеть, тестовое устройство, прокси и логи. Задача — видеть, что приложение делает, и повторять это воспроизводимо.

Архитектура

        [ Интернет ]
             |
   [ Роутер: гостевая сеть / VLAN ]
             |
   ┌─────────┴──────────┐
   |                    |
[ Телефон ]        [ Ноутбук / Pi ]
 тестовый          mitmproxy (WireGuard)
 аккаунт           DNS с логами
 PCAPdroid         Suricata / Zeek
   |                    |
   └───────┬────────────┘
           |
   [ Хранилище: pcap, логи, отчёты ]

Три принципа:

  1. Изоляция. Тестовое устройство не должно видеть домашнюю сеть.
  2. Один вход. Весь трафик идёт через прокси или как минимум через логируемый DNS.
  3. Воспроизводимость. Версия, хеш, конфиг и время фиксируются в манифесте сессии.

Компоненты

Компонент Зачем Варианты Сложность
Изоляция Не пустить устройство в LAN Гостевая сеть + client isolation; OpenWrt-зона с forward: REJECT; VLAN низкая / средняя
Прокси Расшифровка HTTP(S) mitmproxy --mode wireguard; regular; transparent низкая / средняя
Захват на устройстве Привязка «пакет → приложение» PCAPdroid (VpnService, без root) низкая
DNS с логами Домены, время, корреляция Pi-hole, AdGuard Home, Unbound низкая
IDS Сигнатуры и аномалии Suricata, Zeek средняя
Форензика Проверка на компрометацию MVT, iVerify низкая / высокая
Хранение Единый таймлайн Loki + Grafana, ELK средняя

Минимальный стенд

Достаточно, чтобы получить первые реальные данные:

  1. Гостевая сеть на роутере, отдельная подсеть, изоляция клиентов, запрет доступа в LAN.
  2. Проверка: с телефона домашний ПК не пингуется, шлюз и прокси-хост доступны.
  3. mitmproxy на ноутбуке: mitmweb --mode wireguard.
  4. WireGuard-клиент на тестовом телефоне, конфиг из mitmproxy.
  5. Сертификат mitmproxy: на Android — системный (root) либо понимание, что часть трафика не расшифруется; на iOS — профиль и явное доверие.
  6. PCAPdroid на телефоне: pcap + фильтр по целевому приложению.
  7. DNS с логами, выдаваемый по DHCP.
  8. adb logcat в файл на всё время сессии.

Проверка работоспособности: открыть https://mitm.it с телефона — должна открыться страница установки сертификата.

Методика эксперимента

Шаг Что делаем Что фиксируем
1 Чистое устройство, тестовый аккаунт Версия ОС, модель, дата
2 Установка приложения Источник, версия, SHA-256
3 Первый запуск без входа Домены, запросы, разрешения
4 Регистрация Новые домены и поля
5 Отправка сообщения Что уходит помимо текста
6 Простой 15 минут, экран выключен Фоновые запросы
7 Перезагрузка Автозапуск, повторные запросы

Правила:

  • минимум три прогона на сценарий;
  • baseline — отдельная серия, отклонения считаем относительно неё;
  • один сценарий — одна переменная;
  • всё, что не удалось увидеть, записываем как слепую зону, а не как «ничего не найдено».

Что считать аномалией

  • Новый домен, которого не было в baseline.
  • Соединение в фоне при выключенном экране.
  • Передача данных в простое.
  • Обращение к нестандартным портам.
  • Падение приложения при включённом прокси — это сигнал pinning, а не «сеть сломалась».

Что стенд не покажет

  • Содержимое E2EE-мессенджеров: видны только метаданные.
  • Трафик через QUIC, если приложение не уходит на TCP.
  • Соединения с pinning без модификации клиента.
  • Поведение на мобильном интернете, если устройство уходит с Wi-Fi.
  • Серверную часть и то, что приложение хранит на диске.
  • Наличие шпионского ПО: сетевые метрики этого не доказывают.

Уровни

Уровень Железо Что появляется
Минимальный Роутер + ноутбук + телефон Изоляция, прокси, PCAPdroid, DNS-логи
Средний + Raspberry Pi или мини-ПК Постоянные DNS-логи, pcap на зеркале, adb-пайплайн
Продвинутый + коммутатор с зеркалом, NAS VLAN, IDS, единое хранилище, длинный baseline

Начинать с минимального: большинство выводов делается на нём, а продвинутый уровень без методики даёт только красивые дашборды.

Хранение и приватность

  • Тестовый аккаунт без персональных данных; в идеале — без реальных контактов.
  • В логах минимизировать: тела сообщений не нужны, нужны поля и домены.
  • Срок хранения 30–90 дней, затем удаление.
  • Архивы pcap — шифровать (age, GPG), хранить с контрольной суммой.
  • Не выгружать дампы в облачные сервисы.
  • 152-ФЗ: если в трафике есть данные третьих лиц, вы — оператор, со всеми обязанностями.

Границы

Стенд — только для своих устройств и аккаунтов. Перехват чужого трафика не является «расширением методики»: это другое действие с другими правовыми последствиями.

И отдельно: стенд не заменяет EDR. Он отвечает на вопрос «куда приложение ходит», а не «заражено ли устройство». Для второго — MVT и проверка артефактов.
